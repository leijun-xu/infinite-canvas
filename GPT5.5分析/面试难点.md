# Infinite Canvas 项目面试难点

这个项目最大的难点不是调用大模型，而是让 Agent 安全、稳定地操作真实业务页面。面试时可以重点介绍以下四点。

## 1. 打通 Agent 工具执行闭环

项目涉及三套通信方式：

```text
浏览器 ← HTTP/SSE → Canvas Agent
Canvas Agent ← JSON-RPC/stdin/stdout → Codex
Codex ← MCP → Canvas Tools
```

难点是把模型的结构化工具调用转换为浏览器能够执行的画布操作：

```text
用户意图
  → Codex 推理
  → MCP tools/call
  → SSE tool_call
  → 浏览器 applyOps()
  → POST /canvas/result
  → Codex 继续推理
```

### 面试表达

> 我设计了一套 MCP、JSON-RPC、SSE 组合的 Agent 执行链路，让大模型不仅能回答问题，还能读取和修改真实画布。

## 2. 解决流式消息一致性

Agent 消息同时来自：

- Codex 权威历史
- SSE 实时事件
- 内存重放缓存
- `codex-event-history.json` 补充历史

如果处理不好，就会出现消息重复、顺序错乱、刷新后丢失或任务一直显示运行中。

项目使用以下组合确定消息归属：

```text
threadId + turnId + itemId
```

并实现：

- 实时消息合并
- 事件重放
- `replayed` 副作用拦截
- 权威历史覆盖
- 前端 ACK 清理缓存
- Agent 重启后的补充历史恢复

### 面试表达

> 我重点解决了流式事件与历史快照之间的一致性问题，建立了实时事件、重放缓存和权威历史的分层恢复机制。

## 3. 保证 Agent 操作安全可控

Codex 不能直接修改 Zustand 或 IndexedDB，浏览器才是业务状态的唯一执行者。

项目通过以下机制控制 Agent 操作：

- Zod 校验工具参数
- 读写工具分类
- 写操作人工确认
- `requestId` 匹配异步结果
- `clientId` 校验目标标签页
- 工具超时和错误回传
- `applyOps()` 统一修改画布
- 撤销、拒绝和中断能力

### 面试表达

> 我没有让 Agent 直接操作页面状态，而是设计了可确认、可执行、可回传的工具协议，保证模型操作具备明确的安全边界。

## 4. 多标签页和断线恢复

多个标签页可能同时连接同一个本地 Agent，需要避免：

- 工具发到错误页面
- 不同画布快照串用
- 复制标签页导致 `clientId` 冲突
- SSE 断开后遗漏事件

项目使用：

- `sessionStorage` 保存标签页 `clientId`
- Web Locks 处理重复标签页
- `targetClientId` 固定 Turn 的执行页面
- 页面激活时更新目标画布
- SSE 心跳、自动重连和事件重放

### 面试表达

> 我实现了基于 clientId 和 Web Locks 的多标签页隔离，并通过 SSE 重连和事件重放保证任务连续性。

## 一分钟总结

> 这个项目最难的部分，是把 Codex 从聊天模型变成能够操作无限画布的业务 Agent。我打通了浏览器、Canvas Agent、Codex Runtime 和 MCP 之间的通信链路，并重点解决了流式消息一致性、断线恢复、多标签页隔离以及写操作安全确认问题，最终形成了一个可确认、可执行、可回传、可恢复的 Agent 闭环。
